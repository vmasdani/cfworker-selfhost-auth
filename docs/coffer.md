# Coffer

Zero-knowledge secrets manager on Cloudflare Workers + D1. Teams keep secrets per project and environment in a web
dashboard; apps fetch them over a REST API with a one-file client. Secret names and values are encrypted on the client.
The server stores ciphertext, public keys and verifiers.

## Concepts

- **Project**: a set of environments, shared with members. Roles: `owner` (manages members, client IDs and
  environments) and `member` (reads and edits secrets).
- **Environment** (`dev`, `staging`, `prod`, …): its own key and its own secrets.
- **Secret**: name and value, both encrypted. Every change keeps the previous version in history (ciphertext).
- **Client ID**: credentials for one app or CI job, bound to **one environment**, read-only or read-write.
  `COFFER_CLIENT_ID=cfi_…` is public; `COFFER_CLIENT_SECRET=cfs_…` is generated in the browser, shown once and never
  sent to the server.

Accounts work as in Tumbler (`packages/worker-accounts`): installer-created first admin, single-use invite links,
password + optional TOTP two-step login, recovery key shown once.

## Key hierarchy

```
password ─PBKDF2(600k)+HKDF─▶ wrap key ─▶ vault key (random)          recovery key ─HKDF─▶ second wrap of vault key
vault key ─AES-GCM─▶ user's ECDH P-256 private key                     (public key stored in clear)
project key (random) ─ECDH(ephemeral, member public key)+HKDF+AES-GCM─▶ one wrap per member
project key ─AES-GCM─▶ environment key (random), one per environment
environment key ─HKDF─▶ secret-enc key   (AES-256-GCM of {"name","value"})
                ─HKDF─▶ secret-index key (HMAC-SHA256(name) = name_mac, how rows are addressed)
client secret ─HKDF─▶ machine-auth key (server stores HMAC(SERVER_SECRET, it))
              ─HKDF─▶ machine-wrap key ─AES-GCM─▶ environment key, one wrap per client ID
```

Every AES-GCM ciphertext has associated data naming what it is and where it belongs, so the server cannot move
ciphertext between users, projects, environments, client IDs or secret names without decryption failing:

| Ciphertext | AAD |
|---|---|
| user private key | `coffer/v1/user-private-key/<userId>` |
| project key for a member | `coffer/v1/project-key/<projectId>/<userId>` (HKDF info `coffer/v1/member-wrap/<projectId>/<userId>`) |
| environment key | `coffer/v1/env-key/<envId>` |
| environment key for a client ID | `coffer/v1/machine-key/<clientId>` |
| secret | `coffer/v1/secret/<envId>/<name_mac>`; the decrypted name must also hash to `name_mac` |

IDs are generated by the client before the server sees them, because they are bound into the ciphertext.

## REST API for apps (`/api/v1`)

`Authorization: Bearer <client id>.<base64 HKDF(client secret, "coffer/v1/machine-auth")>`

| Method | Path | |
|---|---|---|
| GET | `/api/v1/identity` | project, environment, scope, `envId`, wrapped environment key |
| GET | `/api/v1/secrets` | all rows `{mac, iv, ct, version, updatedAt}` |
| GET | `/api/v1/secrets/:mac` | one row, 404 if missing |
| PUT | `/api/v1/secrets/:mac` | `{iv, ct}`; create or replace (read-write client IDs only) |
| DELETE | `/api/v1/secrets/:mac` | `{deleted}` (read-write only) |

HKDF is HKDF-SHA256 with a 32-byte zero salt and 32-byte output; `mac` is lowercase hex; `iv` and `ct` are base64 and
`ct` ends with the 16-byte GCM tag. Every client file in `apps/coffer/sdk/` documents the same protocol in its header,
and `scripts/sdk-matrix.ts` checks that all of them interoperate.

The clients use only standard libraries: WebCrypto and fetch (TS), `crypto/hkdf` and `net/http` (Go 1.24+),
`HKDF`/`AesGcm`/`HttpClient` (.NET 8+), `hash_hkdf`/`openssl`/`curl` (PHP 8.1+). Python has no AES-GCM in its standard
library, so a Python client would need the `cryptography` package.

## Threats and mitigations

| Threat | Mitigation | Residual risk |
|---|---|---|
| D1 leaked | Names and values encrypted; keys wrapped; verifiers are HMACs with `SERVER_SECRET` | Metadata: project and environment names, member lists, secret count, sizes and change times |
| Client secret leaked | Scoped to one environment and read-only by default; revoke in Access | Attacker reads (or, if read-write, changes) that environment until revoked |
| Client ID and secret leaked together with D1 | Same as above, for one environment only | Other environments stay protected by their own keys |
| Malicious server substitutes a public key when a member is added | Owners see the new member's key fingerprint; members see theirs under Account → Your key; compare out of band | Not enforced: an unchecked substitution exposes that project's key |
| Removed member | Server stops serving them rows | Keys are not rotated: anyone who kept a key or a plaintext copy keeps it. Rotate the secrets themselves |
| Server swaps or replays ciphertext | AAD binds every ciphertext to its location; names re-checked against `name_mac` | Server can serve an older version of a secret (rollback) or hide rows |
| Malicious JavaScript served (Cloudflare account takeover) | Hardware key on the Cloudflare account | Same as any web vault: the dashboard could capture passwords. The SDK files run in your app, not from the server |
| Brute force of client credentials | 256-bit secrets; per client ID and per IP failure limits | — |

Rotation of project and environment keys (re-encrypt everything and rewrap for remaining members) is not implemented.
